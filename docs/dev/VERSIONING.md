# 版本策略

> 2026-10-13 重新定义（世代模型）。定案背景与取舍见 [ADR-0001](../adr/0001-version-renumbering.md)；历史称呼与本文旧定义的对应关系见「历史编号映射」。

## 世代模型

| 世代 | 内容 | 编号 | 状态 |
|---|---|---|---|
| 史前 | MinatoLauncher（更名前） | 不编号（仅历史名称） | 已结束 |
| 初代 | KazariPlay 初代（旧界面；含无翻译分离与 P0/P1 修复） | `0.x`（`0.1.0`～`0.5.0`） | 已结束 |
| 当代 | KazariPlay 新界面（主界面重构起） | `1.x`（`1.0.0` 起） | 开发中 |

- `0.x` 按 semver 语义为初始开发期（允许大改）；`1.0.0` = 新界面世代的第一个正式版（稳定宣告）。
- `1.0.0` 起严格 semver：主版本只在不兼容变化时 +1；新功能 → 次版本；修复 → 修订。
- 世代变化本身不自动升主版本；主版本号只按兼容性契约（用户数据库 / 配置 / 数据目录可无损沿用）判定。

## 编号生命周期（develop ↔ main）

- **核心号（主.次.修订）随 `main` 落定**：一次发布 = `main` 更新 = 按该批内容的最高级别变化定级（有不兼容 → 主版本；有功能 → 次版本；只有修复 → 修订）。
- **develop 开发期间**：`下一个目标核心号-beta.N`。`-beta.N` 是**自测包计数器**——每打一个本机自测包 +1（从 `beta.1` 起）；beta 包仅本机自测，不对外发布。
- **合并 `main` 发布**：去掉 `-beta.N` 后缀、核心号定稿（如 `1.0.0`），打 tag `v<核心号>`、建 GitHub Release；发布门槛为完成实机复验且无未解决 P0/P1。
- 不再使用构建批次后缀（原 `-rN` 已取消）：输出目录与包名直接使用完整版本（`trial-build-1.0.0-beta.1`），一个号对应一个包；同号不允许重打（重打即下一个 `beta.N`）。
- `-rc.N` 为可选的冻结候选标识，仅在需要“冻结候选、批量回归但暂不发布”时使用，不强制。

## 产品线

| 产品线 | 分支 | 编号 |
|---|---|---|
| 无翻译原版 | `develop` | 世代编号主线（当前 `1.0.0-beta.N`） |
| Hook/翻译实验版 | `feature/hook-translation` | 主版本跟随原版，后缀 `-exp.N`（旧 `-experimental.N` 的简写）独立递增 |

- 两线只共享选择性 cherry-pick 的公共修复，不共享发布节奏；实验版现行 `1.4.0-experimental.1` 自下次交付起改用 `1.0.0-exp.N`。
- Beta 与 Exp 是不同产品线，不通过预发布字符串比较决定谁替代谁，也不整分支互相合并。

## 唯一来源与书写

- `kazari_play/version.py` 是运行时版本与产品线的唯一来源（`VERSION`、`PRODUCT_LINE`）；显示版本为 `v<VERSION>`，入口、窗口标题、关于页、启动日志与打包 spec 均从它派生。
- 统一书写：机器、文档、包名、tag 一律规范写法 `1.0.0-beta.4`；展示层 `v1.0.0-beta.4`。不再使用 `V1.4.0 Beta 1` 式空格写法（历史发行说明原文除外）。
- 前端构建元数据 `kazari_play/ui/web_assets/package.json` 与 `package-lock.json` 同步同一版本串。

## 换版同步清单

每次换号（含 `-beta.N` 递增）至少同步：

1. `kazari_play/version.py`
2. `kazari_play/ui/web_assets/package.json`、`package-lock.json`
3. `README.md`（标题与版本说明）
4. `RELEASE_NOTES.md`（当前版本行）
5. 本文「世代模型 / 产品线」表
6. `docs/README.md` 文档状态行
7. `AGENTS.md` 当前状态
8. `CHANGELOG.md` 记录换版

`tests/verify_frontend.py` 校验 `version.py`、前端构建元数据与 `README.md` 的版本串一致，不一致即失败。
