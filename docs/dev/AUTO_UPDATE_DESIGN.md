# KazariPlay 自动更新设计

> 状态：**v0.9（2026-10-17）：已实施（阶段 A–E 完成；E2 真实更新演练待首次正式发布后执行）。** v0.7 为代码审查（UPD-REV-01～13）后的修复；v0.8 增加**更新提速与就绪复用**（通道切换、就绪缓存、分阶段埋点、单入口应用方式）；v0.9 增加**启动本地探测就绪并自动提示**（预发布同样适用）。见 [更新提速与就绪复用计划](AUTO_UPDATE_SPEEDUP_PLAN.md)。决策依据为 2026-10-13 逐轮问答与三份开源参考的对照（见 §0）。
> **最高原则**：**① 用户数据保护第一**——更新流程任何环节都不得损坏、丢失或搬移用户数据；**② 原生无感体验**——更新存在感尽量低、界面融入应用自身视觉，不做第三方工具风格的独立窗口。
> 质量标准：按**对外多人分发**设计（清晰错误、可回滚、不静默失败）。
> 范围：应用内自动更新（检查 / 提示 / 下载 / 替换 / 回滚）；目标形态为便携文件夹版（PyInstaller onedir，数据在包旁 `data/`）。

## 1. 目标与边界

- 对外分发的正式版可自动升级到新的正式版；更新源为 **GitHub API**（仓库 `SB-TDM/KazariPlay`，公开）。
- 支持形态：便携文件夹版（`KazariPlay.exe` + `_internal/` + 附随文档；数据在包旁 `data/`）。
- **不做（v1）**：源码运行的自动更新（界面提示用发布包）；安装器；抢先体验渠道；断点续传；文件级增量更新。
- 带预发布后缀（`-beta.N` / `-exp.N`）的包默认**关闭自动检查**（关于页可手动检查）；更新只认正式 Release。
- 自动更新自 `1.0.0` 起随包发布——第一个正式版必须包含本功能，后续版本才能自助升级。

## 2. 数据保护（最高原则的落地）

- **替换白名单**：更新只替换 `KazariPlay.exe`、`_internal/` 与附随说明文档；`data/`、`screenshots/`、`logs/` 永不进入替换集，助手在替换前对路径做**代码级断言**（命中禁用区即中止）。
- **更新前自动备份**：替换前把 `data/games.db` 与 `data/config.json` 复制到 `data/backup/<时间戳>/`，滚动保留最近 **3** 份。
- **失败语义**：下载/校验失败 → 不进入替换阶段；替换阶段失败 → 用 `_old/` **自动回滚**；**替换成功但新版无法启动** → 健康检查触发回滚（见 §6）；无论成败**必拉起可用版本**（成功=新版，失败/取消=旧版）——绝不把用户留在"没有应用"或"坏包"状态。
- **校验失败必须终止，不提供绕过**（明确拒绝 XiaoqiangUpdater 式"风险自负继续安装"）。
- 更新器**不读取、不迁移、不重写**任何用户数据文件；数据库结构迁移只由新版启动时自带的既有迁移流程（`_ensure_column`）完成。
- **数据位置原则**：便携包 `data/` 随包存放；分发文档与包内 README 建议解压到**非系统盘**；更新器不向 `C:` / `%APPDATA%` 写入任何数据；图片类数据（covers / screenshots）在便携模型下始终位于包内 `data/`，不入 `%APPDATA%`。**不要解压到需要管理员权限的目录**（`Program Files`、`Windows` 等）或受控文件夹访问（CFA）保护目录；数据目录不可写时**启动即报错**（用户可读文案），不做静默降级。（源码运行模式的 `%APPDATA%` 路径属开发模式遗留，图片数据不在 `%APPDATA%` 的方向记为后续优化。）

## 3. 体验（第二原则的落地）

- **应用内弹层**（复用现有 Kawaii 组件视觉），不做独立更新器窗口；**无更新零打扰**，启动发现新版只提示一次；24h 检查缓存。
- 下载进度展示：百分比 / 已下载 / 总大小 / **速度 / 剩余时间**（复用批量进度条组件）；**下载中禁止关闭弹层**。
- 更新执行尽量无感：助手**无窗口**（无黑框闪窗）、零交互替换；完成后自动启动新版。
- 完成选项：**仅「立即重启更新」**（2026-10-14 移除退出时更新）；想稍后处理可关闭弹层/关应用，就绪缓存保证重启后 0 重下。
- 失败界面：**重试 / 打开发布页（手动更新兜底）/ 退出**。
- 更新完成：新版首启 toast「已更新到 vX」（仅更新后首次启动）。
- 启动自动提示（2026-10-17）：本地存在就绪缓存时，启动自动提示一次（预发布同样适用，标题标注"基于上次检查"），无需先手动检查。
- "**跳过此版本**"记入 `config.json`（`update.skipped_version`），不再提示该版本。

## 4. 更新源与资产契约

- 检查：`GET https://api.github.com/repos/SB-TDM/KazariPlay/releases/latest`（未认证；遵守系统代理；24h 缓存；60 次/小时限流足够）。
  - 读取：`tag_name`（`v1.0.1` → `1.0.1`）、`body`（更新说明）、`assets[]`。
- **下载通道（2026-10-14）**：候选顺序「**记忆通道**（`update.last_good_lane`）→ 直连 → 镜像前缀」；单通道 socket 超时 **10s**、下载开始 **15s 单次低速检查**（已收 <5MiB 即切）、候选链 **1 轮**；切换静默从零重传；镜像只承担传输，不改变校验信任。默认镜像 `gh-proxy.com / ghfast.top / ghproxy.net`（`config.update.mirror_prefixes` 可覆盖）。
- **就绪缓存（2026-10-14）**：`update_cache/ready.json` 记录 `{tag, version, asset_name, digest, zip, ts}`；检查命中 tag+摘要且 zip 完好时**跳过下载**直接 `ready`（解压目录按需重建）；检查失败但本地就绪有效时允许**离线就绪**（标注"基于上次检查"）；确认成功后先删记录再清缓存。
- **校验信任（2026-10-14）**：SHA256 期望值优先取**发布元数据**（GitHub API 响应中的资产 `digest`）；无摘要时仅接受**官方源直连**的 `SHA256SUMS.txt`。镜像只承担文件传输，**不得**用镜像自报的校验文本充当信任（可信校验不可得即失败，不降级）。
- 发布资产（固定命名，**按平台参数化**）：
  - `KazariPlay-<平台标签>.zip`：干净包（程序文件 + 包内资源；**不含** `data/`、构建缓存、会话产物）；当前平台标签仅 `win64`，对外文件名不变。
  - `SHA256SUMS.txt`：含各平台 zip 的 SHA256。
  - 备用直链（不依赖 API）：`https://github.com/SB-TDM/KazariPlay/releases/latest/download/KazariPlay-win64.zip`。
  - **平台接缝**：更新器按运行时平台（`platform.system()` + 架构）选择资产；`BUILD_INFO.json` 记录 platform/arch；将来新增平台（`macos-arm64`、`linux-x64` 等）只**增加**资产文件，旧客户端只查找自己平台的资产名——**不破坏旧客户端**（无需先升级更新器）。
- 版本比较：`主.次.修订` 三元组；预发布后缀版本默认视为"不提示更新"。

## 5. 流程状态机

```
Idle ─启动后台检查(24h 缓存) / 关于页手动─> Checking
启动 ─本地探测就绪缓存(不联网)─> Ready（预发布/静默检查被禁用时；标注"基于上次检查"）
Checking ─无新版─> Up-to-date
Checking ─命中就绪缓存(tag+摘要一致，zip 完好)─> Ready（不下载；离线时标注"基于上次检查"）
Checking ─有新版─> Available ──────────── 弹层：版本 / 大小 / 说明摘要
   │                                        [跳过此版本] [稍后] [下载并更新]
   ├─跳过─> Skipped（记入 config；同时清理就绪缓存）
   └─下载并更新─> Downloading（通道：记忆→直连→镜像；10s 超时 + 15s 单次低速检查；1 轮）
Downloading ─网络/校验失败─> Failed（重试 / 打开发布页 / 退出；日志）
Downloading ─SHA256 通过─> Ready（写 ready.json + 保留 zip）
Ready ─立即重启更新─> Applying（拉起助手，主程序退出）
（Ready 可关闭弹层/关应用：下次检查命中就绪缓存，0 重下）
Applying ─备份数据 → 白名单替换成功─> 启动新版（_old 暂不清理）
Applying ─拉起新版异常 / 新版确认前退出─> 立即回滚 → 启动旧版 + 明确提示
新版 ─前端首屏数据加载成功（就绪握手）─> Verified（清理 _old / 缓存 / ready.json）
新版 ─连续两次启动未完成握手─> 回滚助手：等待进程退出 → 恢复 _old → 启动旧版 + 明确提示（健康检查）
Applying ─替换失败─> 自动回滚旧文件 → 启动旧版 + 明确提示
```

## 6. 更新助手（新版本 exe 的 `--apply-update` 模式）

- 主程序在退出前拉起：`<新包解压目录>\KazariPlay.exe --apply-update --pid <旧进程ID> --target <安装目录>`。
- 助手步骤：
  1. 等待旧进程及子进程退出（WebView2 子进程持有文件；超时按进程树强杀并**确认退出**，无法确认即中止，不进入备份与替换）；
  2. **备份用户数据**（`data/games.db`、`data/config.json` → `data/backup/`，滚动 3 份；备份失败即中止，不进入替换）；
  3. 目标程序文件备份到 `_old\<时间戳>\`；
  4. 按**白名单 + 路径断言**原子复制新程序文件（状态文件原子写入，写不进即中止/回滚）；
  5. 成功：写入"待验证"并启动新版；**拉起异常或新版在启动确认前退出 → 立即回滚并拉起旧版**；`_old\` 保留至新版首启成功——新版**前端首屏数据加载成功（就绪握手）**后才完成确认、清理 `_old\` 与临时目录；
  6. **启动自愈与健康检查**：新版启动时先检查"待确认"状态——连续两次启动未完成握手则**回滚 `_old\`** 并启动旧版；否则清理上次更新残留。覆盖"替换成功但起不来"的场景（杀软隔离新 exe、WebView2 环境受损等）。
- **回滚助手（2026-10-14）**：自愈需要回滚时不再由运行中进程原位覆盖自身 EXE，而是从**更新解压缓存**拉起独立回滚助手（`--apply-rollback`）：等待当前进程退出 → 从 `_old\` 恢复 → 写入回滚状态 → 拉起旧版。助手拉起失败时保留状态、备份与可诊断错误，不误报成功、不谎报"已回滚"。
- **互斥**：应用侧拉起更新为**单入口**，原子占用防重复点击/重试；助手侧对安装目录加锁（陈旧锁按 PID 清理），同一安装目录至多一个替换任务。
- **埋点（2026-10-14）**：助手记录 `wait_exit / backup_data / backup_program / replace / launch / 总计` 耗时；拉起后早期退出观察窗口 **8s**（慢崩交给开机两振）；新版记录「入口→窗口就绪/前端就绪」耗时。
- **残留清理（2026-10-14）**：启动自愈删除安装根目录白名单条目的 `*.new`；确认成功时先删 `ready.json` 再清缓存。
- 助手无窗口运行；日志：`logs/update.log`。
- 助手**不请求提权**（不触发 UAC、不 runas）：应用与助手同为普通用户权限运行；权限不足一律走失败语义（不进入替换 → 回滚 → 拉起旧版），不弹管理员授权。
- **更新后健康检查（两段确认）**：新版前端就绪（首屏数据加载成功、经桥握手）后才清理 `_old\`；若新版起不来（握手缺失），自动回滚并启动旧版。
- **WebView2 显式检测**：启动前检测 WebView2 Runtime 可用性，缺失时明确提示并给出安装指引（winget / 官方引导链接），不让 pywebview 抛出原始报错。

## 7. 发布流程配套（增补到 PACKAGING 清单）

每次正式发布产出三件套（**按平台**）：

1. `KazariPlay-<平台标签>.zip`——干净包（固定名，不带版本；zip 内 `BUILD_INFO.json` 含真实版本与 platform/arch）；当前只产 `win64`，未来新平台按需**追加**资产，不改既有平台文件名；
2. `SHA256SUMS.txt`——各平台 zip 的 SHA256；
3. Release 正文——更新说明（更新器展示的摘要来源）。

`scripts/package_develop.py --release`：在自测包构建之外，额外生成 ①+②（从干净 tree 构建；拒绝工作区脏状态）。发布与推送仍由维护者在本地执行（不引入 CI）。

## 8. 实现位置

- 后端：`kazari_play/utils/updater.py`（检查/通道切换/可信 SHA256/包结构预检/就绪缓存/磁盘预检/状态机）；`utils/update_apply.py`（`--apply-update` 替换助手、`--apply-rollback` 回滚助手、启动自愈、安装锁、阶段埋点、残留清理）；`ui/web_bridge.py` 暴露 `checkUpdate` / `downloadUpdate` / `applyUpdate`（单入口）/ `getUpdateState` / `updateFrontendReady`（就绪握手，返回完成文案）；`main.py` 入口与启动自愈。
- 前端：`ts/settings.ts` 关于页接线；`ts/updater.ts`（登记 `main.py::_JS_MANIFEST`，串行轮询 + 代际校验）；`ts/app.ts` 首屏数据加载成功后发送就绪握手并 toast 完成提示；进度复用批量进度条组件。
- 配置：`update.enabled`（预留）、`update.last_check`、`update.skipped_version`、`update.mirror_prefixes`（镜像候选）、`update.last_good_lane`（记忆通道）。
- **快速退出**（`ui/web_bridge.py::UPDATE_FAST_EXIT`，默认关闭）：助手拉起成功后 `win.destroy()`，最多 1s 宽限即 `os._exit(0)`；等埋点数据证实 `wait_exit` 为大头后启用。
- **平台中立与接缝**：更新核心（检查 / 通道切换 / SHA256 / 状态机）保持平台无关；替换助手按平台实现并注册（Windows 先行：退出后替换；Unix 系可直接原地替换）；"运行时 → 平台标签"的映射独立成函数，便于后续扩平台。

## 9. 验收（草案）

- **提速与就绪（2026-10-14）**：见 [提速计划 §2](AUTO_UPDATE_SPEEDUP_PLAN.md) 的 A1–A7（死通道惩罚 ≤10s/首进度 ≤12s、就绪复用 0 重下、应用窗口分阶段埋点、安装残留清理、磁盘空间预检、离线就绪）；真实链路复测按该计划 §5 执行。
- **数据保护专项**：替换集路径断言（data/screenshots/logs 命中即拒绝）；备份生成与滚动；备份/状态持久化失败即中止；故障注入（替换中途杀进程）→ 回滚成功、旧版可启动；更新前后 `data/` 内容哈希一致。
- **权限边界**：普通用户账户下完成完整更新链路（全程无 UAC 弹窗）；不可写目录（模拟 `Program Files`）启动报错文案正确；权限不足时走失败语义而非请求提权。
- **健康检查专项**：替换后新版首启失败（模拟：拉起异常 / 确认前早退 / 连续两次未握手）→ 自动回滚并启动旧版；前端就绪握手完成前 `_old\` 不清理，完成后才清理；回滚助手拉起失败时保留状态与备份。
- **依赖检测**：模拟 WebView2 缺失 → 启动给出明确指引而非原始异常。
- 离线：模拟 API 响应（有新版 / 无新版 / 资产缺失 / SHA256 不符 / 直连失败走镜像 / 无可信校验值）→ 状态机与拒绝逻辑断言。
- 集成：本地两版本目录演练替换、回滚、`data/` 保留（不依赖真实发布）；冻结包受控流程用 `scripts/verify_frozen_update.py --package <构建目录>/dist/KazariPlay` 演练（真实进程与文件占用，含握手与数据保全）。
- 真实：发布 `1.0.1` 后由 `1.0.0` 完成一次真实自动更新（首个更新人工验证并记录）。
