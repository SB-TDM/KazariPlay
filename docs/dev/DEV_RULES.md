# KazariPlay 工作约束

> 面向 Agent / 协作者。改代码、打包、发布、提交前先读本文件。
> 这些约束高于通用习惯；与全局规则冲突时，以本文件为准。

---

## 1. 用户数据保护

数据库、配置、封面、截图等**用户数据**不因打包 / 更新 / 清理而丢失。

- 打包前必须**备份打包产物目录里的用户数据**，打包后**恢复**回新产物，临时备份**用完即删**。
- 保护范围：`KazariPlay_V1.0_build\dist\KazariPlay` 根下**除 `_internal\` 和 `*.exe` 之外的所有内容**都视为用户数据。
- 覆盖已有产物的打包脚本必须实现同等的备份 → 打包 → 恢复 → 删除临时备份流程；隔离试用入口拒绝已存在的输出目录，不清空任何已有产物或数据。
- 原则：**用户数据宁可留着，也不许打包流程清掉**。
- `scripts/package_develop.py` 只生成新的隔离试用目录，拒绝覆盖已有输出；通过 `KAZARIPLAY_DATA_DIR` 将包运行数据隔离到包旁 `data/`，不得把真实用户库复制进包。

## 2. 破坏性 / 不可逆操作前置

删除、覆盖、清空目录、`--clean`、`git push --force`、`git filter-branch`、删分支 / worktree、覆盖配置或数据库等**不可逆**动作，执行前依次：

1. 说明它**不可逆**并交代影响面；
2. 做备份，或准备**用完即删**的临时备份；
3. 无法安全备份 / 隔离时，**先问用户**再执行。

纯新建文件、可再生的编译产物（`js/`、`__pycache__` 等）除外。

## 3. 验证门禁

改完不能凭"看起来对"收尾，必须跑**对应层**的门禁：

| 改动类型 | 必跑 |
|---|---|
| 前端 `ts/` / `css/` / `partials/` | `npm run build` + `python tests/verify_frontend.py` |
| 扫描器 `game_scanner` | `python tests/test_scanner.py` |
| 截图相关 | `python tests/smoke_screenshots.py` |
| 任意 `.py` | `py_compile` 语法校验 |
| 数据库 schema 变更 | 用真实库副本跑一次迁移，确认不丢数据 |

- 验证要盖住**根因**，不能只盖报告的样例。
- 改动必须**用源码版启动、实机跑一遍相关流程**才算完成。
- 没跑的项要在汇报里明确标"**未验证**"。

## 4. 提交与推送边界

- **提交范围**：只暂存本次任务相关文件，保护用户已有的无关改动（不 `git add -A` 一把梭）。
- **本地提交时机**：门禁通过 + 范围清晰即可提交，不必等用户再次点头。
- **推送时机**：`git push` **必须用户明确要求**，确认前不推。
- **提交信息一律中文**。
- **禁止**提交密钥 / 敏感信息、提交后再改配置。

## 5. 改动纪律

- **先读后改**：改任何模块前先读上下文（判重、数据流、桥接），不凭文件名臆断。
- **最小根因修复**：改在因果路径上，不顺手重构 / 格式化无关代码。
- **前端唯一真相**：只改 `ts/` 源，`js/` 是编译产物不许手改；改完必须 `npm run build`；新增模块登记 `main.py` 的 `_JS_MANIFEST`。
- **联动点同步**（改一处要同步另一处）：
  - `identity` 判重 ↔ 标题归一化（`utils/title_utils.py`）
  - UISync 域（`ui/sync.py`）↔ 前端 `__app`（`ts/state.ts`）
  - DB schema 变更 ↔ `db_manager` 建表 + `_ensure_column` 迁移
- **不留死代码**：功能删掉后，其专用代码 / 配置一并清理（除非明确保留）。
