# 版本号重新定义：0.x 为初代世代、1.0.0 为新界面世代

> 状态：accepted（2026-10-13）

产品经历三次整体重构：MinatoLauncher（史前）→ KazariPlay 初代（旧界面）→ KazariPlay 新界面（主界面重构起）。旧编号沿用软件自身的 `V1.x`/`1.x`（且 `V1.01`/`V1.2.1` 等写法混用），无法表达世代变化；`1.4.0-beta.1` 一个标识先后被 2026-10-07 自测包与重构早期自测（共 9 个内容不同的包）共用。经用户逐轮定案：历史初代统一映射为 `0.x` 世代（`0.1.0`～`0.5.0`；Minato 不编号），当代从 `1.0.0` 开始；`1.0.0` 起严格 semver，核心号随 `main` 发布定稿，`develop` 期间只递增 `-beta.N` 自测包计数；取消 `-rN` 构建批次；实验版主版本跟随原版、后缀改用 `-exp.N`。

## 备选方案与取舍

- 续用 `1.4.x` 编号：改动最小，但世代变化在号上不可见，痛点未解。
- “显式宣告新世代”作为升主版本的第二理由：更直白，但偏离严格 semver 的客观性，未采用。
- 时间驱动编号（如 `2026.10`）：无法承载功能/修复语义，未采用。
- 保留 `-rN`、`beta.N` 按“验收轮次”递增：一包一号更简单可审计，最终取消 `-rN`、每个自测包递增 `beta.N`。

## 后果

- 历史发行说明、提交与旧自测包目录**不重命名**；对应关系见 [历史编号映射](../dev/VERSIONING.md)。
- 现存 `v1.0.0` 标签（本地与 GitHub 各指向各自的“更名首版”提交）改名 `v0.1.0`（同提交、内容零变化）；`v1.0.0` 留给新界面世代第一个正式版。GitHub 上附于旧标签的 V1.0 Release 按用户明确授权删除，正文保留于 `RELEASE_NOTES.md`。
- `tests/verify_frontend.py` 增加版本一致性校验（`version.py` ↔ 前端构建元数据 ↔ `README.md`）。
- 文档目录同步归类为 `dev/`、`ui/`、`archive/`、`plans/`（与本次重定义同一批次完成）。
