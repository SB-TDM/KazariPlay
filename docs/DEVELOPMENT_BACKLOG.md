## 修复优先级

优先级定义：

- **P0**：会造成用户数据丢失、核心功能不可用或错误操作结果，应在继续扩展功能前修复。

## 审查更正与行为待确认

- **批量选择显示错误不作为已确认缺陷**：`as unknown as number` 是类型断言，不会把字符串转换为数字。运行时 `Game.id` 和 `dataset.id` 都是字符串时，集合仍可以正确匹配。真实问题是 `state.ts` 的游戏 ID 类型与后端契约不符，应随增量删除修复统一；不能据此宣称全选必然失败。
- **重新扫描是否自动更新路径属于产品行为**：已有批量重新定位入口，扫描同一 identity 后跳过不一定是缺陷。保留现状还是自动更新必须先确认，不进行无授权的自动路径迁移。
- **截图操作目标需区分**：节点复用已复现旧图风险，但操作方法读取的是当前游戏 ID，不能仅凭旧 `shot` 闭包断言一定会删除上一个游戏的文件。验收时同时检查预览和操作目标。
- **远端保护状态未验证**：保护规则是否存在、是否符合要求，实施治理前需通过 GitHub API 或设置页核实。

## 验证基线

本次审查使用隔离探针验证了以下问题：

- 临时数据库中编辑游戏会清空 VNDB、Hook、翻译开关和清洗配置。
- 手动添加 `"null"` 不增加数据库记录。
- 批量删除后重扫会新增记录，单个删除不会。
- 不同章节被 identity 判重。
- 手动批量 VNDB 匹配收到的 `cancel_event` 为 `None`。
- 同一秒截图路径相同并发生覆盖。
- 增量删除无法从前端列表移除字符串 ID。
- 重新定位的重复 identity 直接选第一个候选。
- 重新定位不更新自定义启动路径，写库失败仍计为成功。
- 启动器子进程场景下关闭只处理父进程，Hook 仍使用父 PID。
- 不同游戏同名截图节点会被前端复用。

当前仍需实机验证（构建、受控进程与隔离时序回归已通过）：

- 真实游戏的 Textractor 注入与 Hook 点兼容性。
- 启动器→真实游戏的进程树关闭行为，尤其超过 10 秒的延迟启动链。
- WGC/PrintWindow 在不同 DPI、独占全屏和多显示器下的行为。
- 真实 AI 服务的请求超时、延迟返回和多次配置切换；受控 worker 时序测试不能代替服务验收。

## 分支职责与同步规则

| 分支 | 目标职责 | 日常变更来源 |
|---|---|---|
| `main` | 无翻译原版的稳定主线 | 从 `develop` 接收验收通过的变更 |
| `develop` | 无翻译原版的日常集成 | 短期 `fix/*` 或 `feature/*` 工作分支 |
| `feature/hook-translation` | 独立维护现有翻译实验版 | 翻译专属变更及选定的公共修复 |

- `feature/hook-translation` 在本模型下是长期实验分支，不按普通短期功能分支整体合入 `develop` 或 `main`，否则会重新把翻译带回原版。
- 分离以后，公共修复尽量单独成提交，经核对后选择性同步；翻译专用提交留在实验分支。
- 不把原版的翻译移除提交直接合入实验分支，也不对已公开的实验分支反复 rebase 到原版主线，以免删除实验实现或改写共享历史。
- 不重复维护两个独立仓库或整份目录副本。需要并行测试时使用独立工作目录/worktree，防止共用的 `overlay/bin`、前端 `js/` 被另一个版本的构建覆盖。
- 构建开关未定前，按分支构建各自版本；原版依赖和打包清单必须不含翻译能力，不能仅隐藏翻译 UI。

## 分离实施流程

以下保留已确认的实施顺序。版本分离与 P0/P1/P2 本地修复已完成；真实游戏/服务验收和远端待定事项仍待执行：

1. **保存含翻译版本的基线**：先核对实施时的工作区与最新提交，明确处理本次未提交文档。建立实验分支后再移除翻译，保留原始提交和已有标签，不改写历史。
2. **建立隔离工作目录并规划改名**：原版主线目标为 `main`，从保存的基线进行分离。远端分支推送、GitHub 默认分支切换和旧远端 `master` 删除分开处理；第 7 项待定期间不顺手配置保护规则或发布版本，也不自动删除旧分支。
3. **在分离工作分支移除翻译**：处理翻译 UI、桥接口、会话协调、AI 请求、Hook、字幕与文本清洗专用代码和依赖；共享文件只移除翻译调用路径。继续保留截图、截图 toast、游戏库、元数据、多源搜索、进程监控、扫描及重新定位。
4. **保留截图 Overlay 与用户数据**：不得删除整个 `overlay/`。现有 DLL、EXE、OBJ 等本地产物按此前要求保留；原版的新构建及打包只使用截图所需内容，隔离旧实验产物。不得删除用户数据库、配置、封面、截图或为分离而破坏性删除旧库中的翻译字段。
5. **分别验收两条版本线**：原版无翻译入口、API、Hook 注入和翻译依赖，截图 toast 可构建运行；实验分支仍保留翻译能力。验证旧数据库能被原版读取且数据不丢失。两版先用独立测试配置和数据库副本验证，不同时写真实用户库。
6. **建立无翻译集成基线**：无翻译原版验收通过后，`main` 和 `develop` 以该基线开始管理；更新各分支 README、构建步骤、测试范围和待办归属。明确公共修复如何选择性同步。
7. **再安排待办和远端治理**：按 P0/P1/P2 修复对应版本的问题。构建开关、分支保护与正式 Release 等第 6、7 项事项，待用户决定后单独执行。

## 版本分离验收标准

- 无翻译原版保留当前版本的非翻译功能，版本分离本身不夹带无关重构或业务修复。
- 截图 Overlay 源码和构建保留，不能因移除 Textractor/字幕链路而删除截图 toast。
- 原版和实验版分别从干净源码构建，不能借用另一版本的 DLL、EXE 或前端 JS 才能运行。
- 原版没有翻译界面、桥 API、AI 调用或 Textractor 注入；实验版保留这些能力并明确标注实验性。
- 保留已有历史、用户数据和旧 schema 的读取兼容；数据库/配置写入兼容另做回归，不强制重置用户配置。
- `develop` 为无翻译集成线，实验分支不会通过整分支合并意外回流到原版。
- 第 6、7 项保持待定，没有创建构建开关、保护规则、标签或 Release。
